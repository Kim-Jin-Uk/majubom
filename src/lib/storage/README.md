# 이미지 저장소 (R2) — 설계 기록

정본은 `02_기능명세서.md` (FR-PRD-010 · FR-SITE-030 · FR-CHAT-020) 와 `06_기술스택_인프라.md` §이미지.
명세가 정하지 않은 것을 여기서 어떻게 정했는지만 적는다. 결정 기록은 `LATER.md` L-40.

```
variants.ts   순수. 키 규약과 폭 계산. 서버(업로드)와 화면(srcSet)이 같은 파일을 본다
image.ts      sharp. 바이트 → 여러 폭의 webp. 형식 판별·EXIF 처리도 여기
r2.ts         S3 클라이언트, 키 생성, PUT/DELETE, 사업장 용량 집계
../../components/Img.tsx   저장된 URL 하나 → srcSet
app/api/uploads/image      업로드 라우트 (콘솔 전용)
```

## 결정한 것

**브라우저가 R2 에 직접 올리지 않는다.** 예전에는 presigned PUT 이었다. 리사이즈를 업로드 시점에 하려면
서버가 바이트를 봐야 해서 바꿨는데, 바꾸고 나니 원래 있던 구멍 세 개가 같이 닫혔다 —
(1) `image/webp` 로 서명받고 HTML 을 올릴 수 있었다 (2) 사업장 100MB 한도를 올린 **뒤에만** 알 수 있었다
(3) 손님 사진의 EXIF(GPS)가 그대로 공개 URL 에 올라갔다. R2 CORS 설정도 이때 필요 없어졌다.

**크기 목록을 DB 에 저장하지 않는다.** 저장하는 건 가장 큰 것의 URL 하나뿐이다.
`products.images` · `resources.imageUrl` · 리뷰 · 채팅이 각자 "URL + 폭 배열" 형식을 갖게 되면,
사업자가 직접 붙여 넣은 외부 URL 과 섞이는 자리마다 분기가 하나씩 생긴다.
대신 **URL 만 보고 형제 파일을 계산할 수 있게** 규약을 짰다:

```
{businessId}/{kind}/{yyyy}/{mm}/{uuid}/{width}.webp
```

kind 와 폭이 키에 들어 있고, 만드는 규칙이 "그 kind 의 표준 폭 중 원본보다 작은 것 + 원본(상한까지)" 이라
저장된 폭에서 형제 폭이 유일하게 정해진다. `plannedWidths` 와 `siblingWidths` 는 같은 규칙의 양쪽이라
한쪽만 고치면 화면이 없는 파일을 가리킨다 — 테스트가 모든 kind × 경계 폭으로 왕복을 묶어 둔다.

**한도는 자물쇠 대신 되돌리기로 지킨다.** 올리기 전에 한 번 세고, 올린 뒤에 한 번 더 세서 넘치면
**방금 올린 것만 지운다**. 이 구간에는 sharp 와 R2 왕복이 들어 있어 몇 초가 걸리는데, 그동안 DB 자물쇠를 붙들면
같은 사업장의 업로드가 전부 줄을 서고 핸들러가 죽으면 세션 자물쇠가 남는다. 동시에 들어온 둘이 합쳐서 한도를 넘기면
둘 다 물러난다 — 한 쪽만 살리는 것보다 거칠지만, 판정이 늘 안전한 쪽으로 틀리고 넘긴 채로 남는 일이 없다.

**길이를 말하지 않는 요청은 재기 전에 거부한다 (411).** `formData()` 는 몸통을 끝까지 읽어 메모리에 올리므로,
크기 판정은 그전에 `Content-Length` 로 해야 의미가 있다. 헤더가 없을 때 0 으로 읽으면 판정이 **없는 것과 같아서**,
인증된 사용자가 청크 전송으로 헤더만 빼면 임의 크기 body 가 그대로 들어온다(`file.size` 검사는 이미 다 읽은 뒤다 — #178 리뷰).
판정은 `image.ts` 의 `checkDeclaredSize` 하나이고, 숫자가 아닌 값도 없는 것으로 본다 — `Number("abc")` 는 NaN 이라
크기 비교를 전부 통과한다. 브라우저는 `FormData` 본문에 길이를 항상 붙이므로 정상 업로드는 걸리지 않는다.

**사업장이 키 맨 앞에 온다.** 용량 집계와 사업장 삭제가 접두사 하나로 끝난다.
용량 장부를 따로 두지 않는 이유도 같다 — 장부는 R2 와 어긋나는 날이 오지만, 접두사 합계는 지운 만큼 줄어든다.

**원본을 보관하지 않는다.** 사업장당 100MB 안에서 원본이 절반을 먹는다. 다시 그린 파일에는
촬영 위치·기기·시각이 남지 않는다. 대신 EXIF **회전값은 적용**하고 버린다 — 버리기만 하면 폰으로 세로로 찍은 사진이 눕는다.

**webp 하나만 만든다.** avif 까지 만들면 파일 수와 CPU 가 두 배인데, 얻는 건 몇 십 KB 다.

## 아직 안 한 것

- **손님이 올리는 사진** (리뷰 #92 · 채팅 #119). 지금 라우트는 콘솔(OWNER/MANAGER)만 받는다.
  손님 사진은 사업장 100MB 가 아니라 **사용자당 일 30장·100MB**(FR-CHAT-020)로 세야 하는데 그 표가 아직 없다.
  로그인만으로 남의 사업장 접두사에 쓸 수 있게 열어 두면 한도가 없는 쓰기 경로가 된다.
- **지운 사진의 R2 객체 정리.** 상품에서 사진을 빼도 객체는 남는다. 보존 배치(C6, #131)와 같이 만든다.
  그때까지는 용량 집계가 실제보다 크게 나온다 — 한도 판정이 안전한 쪽으로 틀리는 것이라 두었다.
- **커스텀 도메인**(media.majubom.kr). 지금은 r2.dev 개발 URL 이다 (#12).
