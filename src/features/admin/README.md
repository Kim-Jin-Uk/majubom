# 관리자 콘솔 (에픽 #9) — 설계 기록

정본은 `02_기능명세서.md` §3.9 (FR-ADM-010 ~ 060). 명세가 정하지 않은 것을 여기서 어떻게 정했는지만 적는다.
지금 있는 것은 **가입 심사(010, #65)** · **사업장 상태 제어(020, #66)** · **감사 로그 조회(040, #68)** 다.

```
features/admin/businesses.ts   심사 큐 · 승인/반려 · 상태 제어 · 대기 건수
features/admin/audit.ts        감사 로그 **조회** (적재는 lib/audit.ts)
features/admin/ui/             AdminShell · ApplicationsPanel · BusinessesPanel · AuditPanel
app/api/admin/applications(+[id]) · app/api/admin/businesses(+[id]/status) · app/api/admin/audit
app/admin/{,applications,businesses,audit}
```

접근 제어는 프록시가 한다 — `/admin`·`/api/admin` 은 **ADMIN + TOTP 통과**여야 한다. 검사 순서는 **인증 → 역할 → MFA** 이고, 단계마다 답이 다르다:

| 누가 | 페이지 | API |
|---|---|---|
| 비로그인 | `/login?next=…` (307) | 401 `UNAUTHENTICATED` |
| 로그인 · ADMIN 아님 | **404** | **404** `NOT_FOUND` |
| ADMIN · TOTP 미통과 | `/login/totp` | 403 `MFA_REQUIRED` |

**비로그인을 404 로 숨기지 않는 이유**: `/console` 도 똑같이 `/login` 으로 보낸다. 여기서 404 를 내도 "인증이 필요한 경로" 라는
사실 말고는 숨겨지는 것이 없고, 대신 관리자 본인이 북마크로 들어왔을 때 로그인 화면 대신 404 를 보게 된다.
**숨겨야 할 상대는 로그인한 채 `/admin` 을 떠보는 사업자**이고, 그 자리에서는 실제로 404 다.

화면·라우트에도 같은 검사가 한 번 더 있는데, 그건 프록시를 거치지 않는 직접 호출에 대한 이중 방어다.

## 결정한 것

**심사 큐는 이메일 검증을 마친 신청만.** 미검증 신청은 7일 뒤 자동 삭제되는 반쪽 신청이라(C1) 심사 대상이 아니다.
큐에서 빼는 것으로 끝내지 않고 `decideApplication` 도 거부한다 — 목록만 가리면 id 를 직접 넣는 경로가 남는다.
대기 큐는 **오래된 순**이다. 기다린 사람이 먼저다.

**승인은 공개 URL 을 여는 일이다.** 콘솔은 신청 직후부터 열려 있다(사업자가 심사를 기다리는 동안 매장을 준비할 수 있게).
그래서 승인 메일이 안내하는 것은 "이제 콘솔을 쓸 수 있다" 가 아니라 "예약 페이지가 공개됐다" 다.

**사유 없이 남의 가게를 멈추지 않는다.** 반려·정지·차단은 사유가 필수고, 운영자가 쓴 문장이 요약 없이 그대로 사업자에게 간다 —
무엇을 고쳐야 다시 열 수 있는지 알아야 한다.

**차단은 남은 예약을 조용히 지나가지 않는다.** 앞으로 잡힌 `REQUESTED`/`CONFIRMED` 가 있으면 409 `LIVE_RESERVATIONS` 로 한 번 막고,
운영자가 **"함께 취소" 와 "그대로 두기" 중 하나를 고르게** 한다. 기본값을 두면 아무도 읽지 않는다.

**그래서 전이 표에 `ADMIN` 을 넣었다.** `CONFIRMED>CANCELED_BY_BIZ` 는 원래 콘솔(사업자)만 할 수 있었다 —
배치가 확정 예약을 취소하는 경로를 일부러 막아 뒀기 때문이다. 운영자는 배치가 아니라 **사유를 적고 책임을 지는 사람**이라
그 행에 넣었고, 손님에게는 사유가 담긴 취소 메일이 나간다(#57 의 발송 계층). 운영자에게 열린 전이는 취소 둘뿐이다 —
승인·완료·노쇼는 매장의 판단이라 손대지 않는다.

**상태를 먼저 바꾸고 예약을 정리한다.** 순서를 뒤집으면 "취소는 됐는데 차단이 실패한" 상태가 남고, 그건 손님의 예약만
사라진 가장 나쁜 결과다. 이 순서라면 중간에 멈춰도 "차단됐지만 예약이 남음" 이라 운영자가 다시 눌러 이어 갈 수 있다.

**정지·차단은 세션을 끊고, 복구는 끊지 않는다.** 프록시가 매 요청 상태를 다시 보므로 안전에는 이미 문제가 없다.
그래도 끊는 이유는 **안내를 보게 하기 위해서**다 — 상태만 바꾸면 사업자는 콘솔이 왜 안 되는지 모른 채 화면을 새로 고친다.
복구는 끊을 이유가 없다(다시 로그인하게 만들 뿐이다).

**메일은 커밋 뒤에, 실패해도 던지지 않는다.** 롤백된 승인 메일이 나가면 사업자는 열리지도 않은 URL 을 안내받는다.
반대로 메일 실패로 심사가 되돌아가면 큐에 같은 신청이 다시 뜬다. (#57 과 같은 규약)

## 감사 로그 조회 (FR-ADM-040, #68)

**읽기만 한다.** 적재는 `lib/audit.ts` 가 각 기능 트랜잭션 안에서 한다 — 여기서 다시 쓰지 않는다.

**조회 자체는 감사 로그를 남기지 않는다.** 남기면 로그가 조회로 불어나고, 정작 찾던 상태 변경이 조회 기록에 묻힌다.
(`REPORT_VIEW` 는 다르다 — 그건 개인정보를 여는 행위라 누가 봤는지가 증거다.)

**최신순 고정.** 정렬을 고르게 하지 않는다 — 오래된 순으로 훑는 조사는 없다. 대신 기간·행위·사업장·행위자로 좁힌다.

**커서는 `(createdAt, id)` 쌍이다.** `createdAt` 만 쓰면 페이지 경계에서 행이 빠지거나 겹친다 —
배치가 수백 건을 같은 밀리초로 적재하기 때문에 동시각 행이 흔하다. `to` 는 그날을 **포함**한다(사람이 "9/14까지" 라고 쓸 때 9/14 를 빼면 놀란다).

**필터 드롭다운에는 실제로 쌓인 행위만 낸다.** enum 30종을 전부 늘어놓으면 대부분 0건인 목록에서 고르게 되고,
"없는 걸 골랐나" 와 "정말 없나" 가 구분되지 않는다. 옆에 건수를 붙인다.

**연락처·이메일은 여기서 가릴 것이 없다.** 적재 시점에 `hashPii` 를 거쳐 이미 64자 hex 다 — 복원할 수도 없다.
화면이 그걸 원문처럼 보여 주면 안 되므로 `해시 a1b2c3d4…` 로 줄여 그린다.

**조건을 URL 에 얹지 않는다.** 사업장 목록과 다른 선택인데, 조사 중에 짚은 조건(이름·이메일 조각)이 주소창에 남아
공유되면 그 자체가 개인정보 단서다. 첫 화면만 서버가 그리고 이후 필터는 클라이언트가 API 로 읽는다.
