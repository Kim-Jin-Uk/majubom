# 고객 마이페이지 (에픽 #12) — 설계 기록

정본은 `02_기능명세서.md` FR-BOOK-090(예약 목록·상세) · FR-NOTI-030(알림 채널·설치된 기기).
명세가 정하지 않은 것을 여기서 어떻게 정했는지만 적는다.

```
features/me/notification-rules.ts   알림 채널 규칙 — 순수
features/me/profile.ts              프로필·알림 채널 읽기/쓰기
features/me/ui/                     ProfileForm · NotificationPrefs
features/booking/my-reservations.ts 목록 · 상세 (예약 도메인이라 booking 아래)
features/booking/ics.ts             캘린더 파일 — 순수
app/me/{,reservations,reservations/[id],sessions}
app/api/me/{profile,notifications,reservations/[id]/cancel,reservations/[id]/ics,sessions}
```

## 결정한 것

**목록은 탭, 액션은 상세에.** 두 목록을 세로로 쌓으면 지난 예약이 쌓인 뒤 다가오는 예약을 보려고
스크롤을 올려야 한다 — 손님이 이 화면에 오는 이유의 대부분은 다가오는 쪽이다. 탭 상태는 주소에 두지 않는다
(위젯의 선택과 달리 공유할 일도 뒤로가기로 돌아올 일도 없고, 오히려 "내 예약" 링크가 지난 탭을 여는 일이 생긴다).
취소·변경·캘린더를 카드마다 붙이면 손님이 잘못 누를 자리만 넷 는다. 목록에 남기는 것은 **예약번호**다 —
전화로 말할 값이 그것이다.

**남의 예약 id 는 404.** 403 은 "그 id 의 예약은 있다" 를 알려 주는 꼴이라, 조회 계층이 아예
본인 것만 찾고 없으면 없는 페이지가 된다.

**취소 가능 여부는 화면이 계산하지 않는다.** 전이 규칙(`customerCancelState`)이 판정한 것을 그대로 쓴다 —
화면이 제 식으로 세면 버튼은 살아 있는데 누르면 409 가 나거나, 될 수 있는 취소를 화면이 먼저 막아 손님이 전화한다.
마감이 지난 건에는 **매장 전화**를 크게 둔다. 그때 손님이 할 수 있는 유일한 일이다.

**시간 변경은 위젯에 `replaces` 를 달아 보낸다** (FR-BOOK-050 — 서버는 이미 있었다). 변경 중에는
상품을 바꿀 수 없게 잠근다: 서버가 같은 상품만 받는데(`PRODUCT_MISMATCH`) 링크를 열어 두면 끝에 가서야
막히고, 그때는 고른 시간까지 다시 골라야 한다. 취소가 막힌 건은 변경도 막는다 — 서버가 원 예약을
취소해야 성립하는 흐름이다.

**진행 이력의 정본은 `reservation_logs`.** 명세가 "상태 변경 이력(누가·언제·무엇을·왜)" 으로 둔 그 테이블이고,
생성도 `fromStatus = null` 한 줄로 남아 시작점을 지어낼 필요가 없다. (감사 로그에도 같은 사건이 있지만
그건 운영자의 전역 로그다.) **누가 했는지는 내보내지 않는다** — 매장 안에서 누가 눌렀는지는 매장 사정이다.
사유는 **이미 손님에게 메일로 나간 전이의 것만** 보여 준다(`customerMailFor`). 완료↔노쇼 교정처럼
매장이 내부에 적은 사유는 손님이 볼 문장으로 쓰인 적이 없다.

**캘린더는 `.ics` 파일 하나.** 구글·애플 연동(OAuth)을 붙이면 예약 하나 담자고 캘린더 전체 쓰기 권한을
받아야 한다. UID 를 예약번호로 둬서 두 번 담아도 일정이 늘지 않는다. 시각은 UTC 순간으로 적는다 —
벽시계로 적으면 `VTIMEZONE` 블록이 필요하고, 빠뜨린 파일은 앱마다 다르게 읽어 한 시간 어긋난 일정이 들어간다.
접기(75옥텟)와 이스케이프는 테스트로 묶었다: **깨진 `.ics` 는 오류를 내지 않고 그냥 안 열린다.**

**알림 설정은 행이 없으면 기본값.** 가입할 때 네 행을 미리 만들지 않는다 — 만들어 두면 그룹을 하나 늘리는 날
기존 사용자 전원에게 백필 마이그레이션이 필요해진다. **거래성(예약·근무)의 인앱은 끌 수 없고**(예약이
취소됐다는 사실을 알 길이 아예 없어지면 안 된다), **마케팅은 세 채널 모두 옵트인**이다. 그 규칙은 서버가 지킨다 —
잠긴 채널은 보낸 값과 무관하게 true 로 적는다. 스위치는 누르는 즉시 저장한다(저장 버튼을 두면 켜 놓고
나가 버린 사용자가 안 바뀐 이유를 모른다).

**규칙을 순수 모듈로 뺀 이유.** `notification-rules.ts` 를 `profile.ts` 와 나눈 것은 취향이 아니다 —
클라이언트 컴포넌트가 DB 를 import 하는 모듈에서 규칙을 가져오면 `pg` 가 브라우저 번들로 딸려 들어가
빌드가 깨진다(실제로 그랬다).

**이메일은 마이페이지에서 바꾸지 않는다.** 로그인 아이디이자 알림 폴백 채널이라 새 주소 검증과 세션 처리가
따라붙는다 — 인증 쪽 일이다. 읽기 전용으로 보여 준다.
