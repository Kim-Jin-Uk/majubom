# 사업장 온보딩 · 설정 콘솔 (에픽 #24) — 설계 기록

정본은 `02_기능명세서.md` §3.2 (FR-BIZ-010 ~ 030) · §3.3 (FR-RES-010) 와 기획서 6.1 위저드. 명세가 정하지 않은 것을 여기서 어떻게 정했는지만 적는다.

## 구조

```
app/console/onboarding/[step]   위저드 6단계 (URL 이 단계, 완료 여부는 실제 데이터로 판정 — 진행 상태를 저장하지 않는다)
app/console/settings            OWNER 전용: 기본정보·영업시간·공개 주소·예약 정책 (매니저는 404)
app/console/resources           자원(담당자·공간·공용) + 구성원(매니저 초대·권한·비활성) — 명세 화면 "/console/resources → 매니저 추가"
features/business/settings.ts   영업시간 규칙 · slug 변경(옛 slug 영구 예약) · 1단계 완료 판정
features/business/policy.ts     예약 정책 스키마(범위) · 변경 필드만 감사 diff
features/business/resources.ts  자원 CRUD · 삭제→비활성 대체 규칙 · 정렬
features/business/publish-gate.ts  공개 조건(정보·자원≥1·상품≥1) + 사업장 승인 → 위저드 사이드바·콘솔 홈
features/business/members-admin.ts 매니저 권한 변경 · 비활성화(세션 전부 폐기 + STAFF 자원 비활성)
```

API 는 전부 `app/api/console/*`. 읽기는 소속 멤버 누구나(`requireConsole`), 쓰기는 OWNER(`requireOwner`) + `assertSameOrigin` + `assertWritable`(SUSPENDED 읽기 전용).

## 결정한 것

**완료 판정에 별도 상태가 없다.** "1단계 완료" 는 상호·전화·주소·영업시간 1일 이상·임시 slug(`b-…`) 탈출이 모두 참인 것,
"2단계" 는 활성 자원 ≥ 1, "3단계" 는 활성 상품 ≥ 1 (상품 에픽 #31 전까지는 항상 미완). 선택 단계인 정책은 기본값에서 하나라도
바꿨으면 완료로 본다. 상태 컬럼을 두면 데이터와 어긋날 수 있고, 어긋나면 사용자가 고칠 방법이 없다.

**영업시간.** `close ≤ open` 은 익일 마감(심야 영업). 휴게는 최대 2구간, 영업시간 안, 서로 겹치지 않음. 요일이 배열에 없으면 휴무.
슬롯 계산(#31) 은 이 규칙 그대로 읽는다 — 자정을 넘는 날은 `close + 24h` 로 펼친다.

**slug 는 따로 저장한다.** 한 번 쓴 slug 는 `business_slug_history` 에 남아 다른 사업장이 영원히 못 쓴다(옛 주소 301 의 근거, 공개 홈
에픽 #71). 되돌리기 어려운 변경이라 기본정보 폼과 섞지 않고 버튼을 따로 뒀다. 예약어(`admin`, `console`, `api`, `me` …)는 코드 상수.
자기 사업장의 옛 slug 로 되돌리는 건 허용.

**자원 삭제는 서버가 판단한다.** 예약 이력·상품 연결이 전혀 없으면 물리 삭제, 아니면 비활성화로 대체하고 결과(`mode`)를 돌려준다.
409 로 거절하지 않는다 — 사용자가 원한 것은 "이 자원이 더 예약을 받지 않는 것" 이고 그건 비활성화가 이미 한다.
비활성 자원은 신규 예약 대상에서 빠지고 기존 예약은 유지된다.

**STAFF 자원과 계정은 느슨하게 연결된다.** 자원은 이름만으로 만들 수 있고(memberId null), 매니저 초대가 같은 이름을 자동으로 연결한다
(`features/auth/members.ts`). 자원 편집에서 직접 연결할 수도 있다 — 한 구성원은 자원 하나에만(409 `MEMBER_ALREADY_LINKED`).
사업자 본인도 STAFF 자원이 될 수 있다(1인 사업장).

**slug 변경은 30일 3회.** 옛 slug 가 영구 예약되므로 무제한이면 주소 선점(스쿼팅)에 쓰인다. 가입 때 받은 임시 slug 는 세지 않는다. 초과 → 429 `SLUG_LIMIT`.
`b-` 접두어는 임시 주소 전용이라 고를 수 없다(1단계 완료 판정이 이 접두어를 본다).

**매니저 비활성화 = 즉시 차단.** `revokeAllSessions` 로 리프레시 행을 전부 폐기하고, 콘솔 프록시가 매 요청 세션·memberStatus 를
재확인하므로 다음 요청부터 `/login?reason=REFRESH_REVOKED`. Firebase 리프레시 토큰도 폐기(채팅 플래그가 켜져 있을 때).
연결된 STAFF 자원은 비활성화되고 기존 예약은 유지. OWNER 본인은 대상이 아니다(403 `OWNER_NOT_EDITABLE`) — 이양은 2기.
INVITED(초대 대기) 는 비활성화할 수 없다(409 `NOT_ACTIVE`) — 비활성→재활성 경로로 초대 수락(비밀번호·동의) 없이 ACTIVE 가 되는 걸 막기 위해.
재활성화는 감사 로그를 남기고, 연결된 STAFF 자원은 비활성 상태로 둔다(사장님이 필요할 때 켠다).

**`x-majubom-readonly` 는 프록시만 정한다.** 요청에 실려 온 값은 프록시가 지우고 SUSPENDED 일 때만 다시 붙인다. 클라이언트가 붙여도 자기 요청만 막힐 뿐이지만, 헤더의 출처를 하나로 두는 편이 읽기 쉽다.

**정책 변경은 미래 예약에만.** `Reservation` 이 생성 시점의 `cancelDeadlineHours` 를 스냅샷한다(#31 에서). 정책 PUT 은 전체 교체 —
부분 입력을 받으면 "빠진 키는 기본값인가 기존값인가" 가 애매해진다. 감사 로그 diff 에는 바뀐 키만.

**기능 플래그와 위저드.** 6단계(고객 상담) 는 `FEATURE_CHAT` 이 꺼져 있으면 사이드바에서 아예 사라진다 — 비활성 상태로 보이면 미공개
기능의 존재가 새기 때문(`lib/flags.ts`). 3단계(상품)·4단계(로고) 는 해당 에픽 전까지 안내 문구만.

**pg 오류 코드는 `pgCode(e)` 로 읽는다.** drizzle 0.45 는 드라이버 오류를 `DrizzleQueryError` 로 감싸 원인을 `cause` 에 둔다 — `e.code` 만 보던
`handle()` 의 23505→409 매핑과 자원 삭제의 FK 폴백은 그동안 죽어 있었다(리뷰에서 발견). `features/auth/errors.ts`.

**콘솔 화면은 사업장 한 행을 한 번만 읽는다.** `loadConsoleBusiness` 가 설정·정책·공개 조건(스칼라 서브쿼리 3개)을 한 쿼리로 돌려주고, 페이지는
그것만 쓴다. 이전에는 한 화면에 businesses 를 세 번 읽었다.

**같은 이메일 겸업의 본인 확인은 로그인과 같은 제한을 받는다.** `/api/auth/business-signup` 이 기존 계정 비밀번호를 검사하므로, 백오프·IP 상한·LOGIN_FAIL
기록을 로그인과 공유한다(`assertIdentity`). 로그인 세션으로 붙일 때는 `/api/auth/*` 가 프록시 재확인을 거치지 않으니 라우트가 직접 액세스 만료·세션 폐기를 본다
(`SESSION_STALE`). 동시 신청은 users 행 `FOR UPDATE` 뒤 소속을 다시 본다. "신청과 함께 만든 계정" 판정은 `isPreexistingAccount`(같은 트랜잭션이면 created_at 이 같다).

**반려(REJECTED) 재신청.** 콘솔 홈이 사유와 "다시 신청" 링크를 보이고, `/signup/business` 는 REJECTED 사업자에게만 열려 내용을 채워 준다. 같은 사업자번호로
다시 내면 그 사업장이 PENDING 으로 돌아간다(감사 로그가 참조하므로 새로 만들지 않는다).
