# 리뷰 (에픽 #13) — 설계 기록

정본은 `02_기능명세서.md` §3.8 (FR-REV-010 작성 · FR-REV-020 노출·답글) 과 FR-ADM-060 (신고).
명세가 정하지 않은 것을 여기서 어떻게 정했는지만 적는다.

```
features/review/rules.ts     자격·기한·분포 — 순수 (DB 도 시계도 모른다)
features/review/reviews.ts   작성·수정·삭제 · 공개 목록 · 사업자 답글
features/review/reports.ts   신고 접수 (처리 화면은 관리자 에픽 #70)
features/review/ui/          StarRating · ReviewForm · PublicReviewList · ConsoleReviewList
app/me/reservations/[id]/review · app/site/[slug]/reviews · app/console/reviews
app/api/me/reviews(+[id]) · app/api/console/reviews/[id]/reply · app/api/reviews/[id]/report
```

## 결정한 것

**자격 판정을 순수 모듈로 뺐다.** 예약 상세가 "리뷰 쓰기" 를 언제 보여 줄지와 서버가 요청을 언제 받을지가
갈라지면, 버튼은 있는데 눌러야 409 이거나 쓸 수 있는 사람이 쓸 자리를 못 찾는다. 판정은 `reviewEligibility`
하나이고, **못 쓰는 이유를 구분해 돌려준다** — "안 됩니다" 한 문장으로는 손님이 뭘 해야 할지 모른다
(아직 방문 전인지, 30일이 지났는지, 워크인이라 대상이 아닌지).

**삭제는 `status = DELETED`, 별도 컬럼이 아니다.** 읽는 쪽이 이미 전부 `PUBLISHED` 만 거른다
(공개 홈 요약·최신 3건·목록·평균·분포). 두 번째 축을 만들면 그 모든 질의에 조건이 하나씩 더 붙고,
하나라도 빠뜨리는 날 **지운 리뷰가 다시 보인다** — 손님이 지웠다고 믿은 글이 남의 가게 페이지에 떠 있는 것은
되돌릴 수 없는 종류의 사고다. 신고 이력이 사라지는 것도 아니다(`reports` 행과 감사 로그는 따로 남는다).

**신고된 글도 본인은 지울 수 있다** (명세: "본인 언제든"). 증거가 사라지는 것이 아니다 — 행은 그대로 남고
`reports.targetId` 가 그 행을 가리키므로 관리자는 상태와 무관하게 내용을 읽는다. 관리자가 이미 내린
판단(`HIDDEN`)만 건드리지 않는다.

**지운 뒤 다시 쓰지 못한다.** `reservation_id` unique 가 어차피 막지만, 규칙으로도 막는다 —
"지우고 다시 쓰기" 로 평점을 갈아 치우는 길을 열지 않기 위해서다. 고치는 길은 **7일 이내 1회**로 따로 있다.

**수정은 조건부 UPDATE 다.** 읽고 판정한 뒤 쓰면 같은 순간의 두 요청이 둘 다 통과해 "1회" 가 우회된다
(리뷰 지적). "아직 한 번도 고치지 않았다" 를 WHERE 에 넣어 DB 가 한 번만 성립시키고, 0행이면 그때 읽어
**왜 안 됐는지** 말한다 — 이미 고쳤는지·7일이 지났는지·내려간 글인지는 손님에게 서로 다른 이야기다.

**"1회" 는 칼럼 없이 `updatedAt > createdAt` 으로 센다.** 리뷰 행을 건드리는 다른 경로가 상태 변경
(신고·숨김·삭제)뿐인데, 그 경우는 어차피 본인이 더 고칠 수 있는 상태가 아니다.

**평균·분포는 별점 필터를 타지 않는다.** 3점만 골라 본 손님에게 "평균 3.0" 을 보여 주면 가게의 평점을
잘못 읽는다. 요약은 언제나 전체 기준이고 필터는 목록만 좁힌다. 분포는 **없는 점수도 0 으로 남긴다** —
빼면 막대가 칸을 건너뛰어 "3점이 하나도 없다" 가 안 보인다.

**사업자에게 숨김·삭제 버튼을 만들지 않았다.** 임의로 지울 수 있으면 리뷰를 믿을 이유가 없어진다(기획서 Q4).
사업자가 할 수 있는 것은 **답글**(리뷰당 1건, 수정·삭제 가능)과 **신고**뿐이고, 신고 버튼은 손님 것과 같다.
콘솔 화면이 그 사실을 첫 문단에 적는다 — 없는 버튼을 찾아 헤매지 않도록.

**작성자는 콘솔에서도 마스킹한다.** 사업자는 `reservationId` 로 누구인지 찾을 수 있지만, 화면이 거들 일은 아니다.

**신고하면 그 자리에서 `REPORTED` 로 내린다.** 검토가 끝날 때까지 두면 정말 문제가 있는 글이 며칠 더
가게 페이지에 남는다. 반대로 장난 신고로 멀쩡한 글이 내려갈 수 있는데, **그쪽은 관리자가 되돌릴 수 있다** —
한쪽만 되돌릴 수 있으면 되돌릴 수 있는 쪽으로 기운다. 이미 `HIDDEN` 인 글은 되돌리지 않는다(관리자의 판단이
신고 한 건에 뒤집히면 안 된다). 남용은 **한 사람이 같은 글을 한 번만** 신고할 수 있게 해 막고,
여러 사람이 신고하면 줄이 여러 개 쌓여 그 수 자체가 관리자에게 신호가 된다.

**별점 입력은 라디오 그룹이다.** 버튼 다섯 개로 만들면 키보드로 하나씩 탭해야 하고 스크린리더에
"버튼 1, 버튼 2 …" 로 읽힌다. 라디오면 방향키로 고르고 "3점" 으로 읽힌다.

**가게 머리(`SiteTopBar`)를 꺼냈다.** `/@{slug}` 아래 화면이 늘 때마다 같은 머리를 다시 그리면
언젠가 하나가 달라진다 — 검색으로 들어온 손님이 여기가 마주,봄이라는 걸 알아야 다른 가게도 찾아본다.

## 아직 안 한 것

- **리뷰 사진** (FR-REV-010 최대 3장). 컬럼과 스키마는 열어 뒀지만 업로드를 붙이지 않았다 —
  손님이 올리는 사진은 사업장 한도가 아니라 **사용자당 일 30장·100MB**(FR-CHAT-020)로 세야 하는데
  그 표가 아직 없다. 열어 두면 로그인만으로 우리 저장소에 무한히 쓸 수 있다(`app/api/uploads/image` 주석과 같은 이유)
- **신고 처리 화면** (FR-ADM-060). 큐에 쌓기까지가 여기 몫이고 처리는 관리자 에픽 #70 이다
- **공개 목록 커서 페이지네이션** — 지금은 offset 20건씩. 리뷰가 수백 건인 가게가 없다
- **답글 알림** — 사장님이 답글을 달아도 손님에게 알리지 않는다. 알림 에픽(#95)의 몫
