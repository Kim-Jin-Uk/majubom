# 알림 (에픽 #14) — 설계 기록

정본은 `02_기능명세서.md` §3.10 (FR-NOTI-010 이벤트 · 020 발송 정책 · 030 알림함).
명세가 정하지 않은 것을 여기서 어떻게 정했는지만 적는다.

```
features/notification/events.ts      이벤트 표 — 그룹·채널·이름 (순수)
features/notification/channels.ts    채널 결정 (순수)
features/notification/recipients.ts  수신자 조회
features/notification/notify.ts      적재 + 발송 + 재시도 + 일일 한도
features/notification/inbox.ts       알림함 읽기·읽음·정리
features/notification/ui/            NotificationBell · NotificationList
features/notification/reminder.ts    방문 리마인더 (매시 틱이 부른다)
app/{me,console}/notifications · app/api/me/notifications(+[id]/read, read-all)
app/api/cron/hourly                  매시 틱
```

## 결정한 것

**이벤트 표를 `Record<EventType, …>` 로 둔다.** 그룹·채널·이름 셋 다 그렇다 — 이벤트를 하나 늘렸는데
그룹을 빠뜨리면 사용자가 끄고 켤 수 없는 알림이 되고, 이름을 빠뜨리면 알림함에 빈 줄이 뜬다.
`Record` 면 **빠뜨린 날 컴파일이 깨진다.**

**채널 표는 명세대로 두고, 실제 결정은 따로 한다.** `EVENT_CHANNELS` 에는 `push: true` 가 여럿인데
지금 푸시를 보낼 수단이 없다(에픽 #16). 표를 사실대로 고쳐 두면 에픽 #16 이 들어오는 날 표를 되돌려야 한다 —
표는 명세이고, **"지금 무엇이 나가는가" 는 `channels.ts` 하나가 안다.**

**푸시가 막히면 이메일이 대신한다.** 명세의 채널 결정 순서(설정 → FCM 토큰 → 이메일 폴백)에서 가장 중요한 줄이다.
iOS 미설치 사용자는 푸시가 아예 불가하므로, 폴백이 없으면 "예약 확정" 이 **아무 데로도 가지 않는다.**
원래 이메일을 안 보내던 이벤트(교대 요청 등)도 이때는 메일로 내려간다 — 72시간 시한을 놓치는 것보다 낫다.

**거래성 인앱은 끌 수 없고, 마케팅은 밤에 안 보낸다.** 앞은 "예약이 취소된 사실을 알 길이 아예 없어지면
안 된다" 이고, 뒤는 명세의 21~08시 금지다. 거래성은 시간과 무관하다 — 취소를 아침까지 미룰 수는 없다.

**한도를 넘겨도 인앱은 남긴다.** 인앱 한 줄은 우리 DB 라 한도와 무관하고, 여기까지 막으면 이력조차
남지 않아 "왜 안 왔지" 를 되짚을 수 없다. 숫자와 큐잉은 `LATER.md` L-46.

**인앱 줄을 메일보다 먼저 쓴다.** 그래야 메일이 실패해도 알림함에는 남는다. 메일 최종 실패는
그 줄의 `channels.email` 을 `FAILED` 로 돌린다 — **보냈다고 적힌 이력이 남는 것이 안 보낸 것보다 나쁘다.**
고칠 때는 **방금 넣은 그 줄만** 본다(id): 이벤트·링크로 찾으면 리마인더처럼 링크가 같은 옛 줄까지 뒤집힌다.

**`notify()` 는 던지지 않는다.** 부르는 쪽은 이미 커밋된 일 뒤에 있다. 알림 실패로 예외가 나가면
화면에는 "실패했다" 가 뜨는데 일은 벌어져 있다 (`booking/notify.ts` 가 세운 규약을 그대로 잇는다).

**매장에는 매장이 모르는 일만 알린다.** 새 요청과 만료뿐이다 — 매장이 한 일(확정·거절·취소)을 매장에
다시 알리면 소음이고, 소음이 쌓이면 정작 중요한 줄을 아무도 안 읽는다. 담당자가 없는 예약(공간형·자동 배정)은
사장님에게만 간다: 매니저 전원에게 뿌리면 "내 일이 아닌 알림" 이 쌓인다.

**알림함은 사람 단위다.** `/me/notifications` 와 `/console/notifications` 가 **같은 목록**을 보여 준다 —
알림은 사람에게 오는 것이지 역할에 오는 것이 아니다. 겸업 계정(사장님이면서 손님)이 두 곳을 오가며
같은 줄을 두 번 읽지 않게.

**항목을 누르면 읽음 + 딥링크다.** 읽음만 따로 누르게 하면 아무도 안 누르고 배지 숫자가 영원히 줄지 않는다.
이미 읽은 것은 다시 건드리지 않는다(`readAt is null` 조건) — 읽은 시각이 뒤로 밀리면 "언제 봤나" 가 무의미해진다.

**리마인더의 창은 한 시간이다.** 크론 주기와 같게 맞췄다 — 좁히면 사이로 빠지고 넓히면 두 번 간다.
**멱등성의 전부는 `not exists` 한 줄**이다(이미 적재한 예약은 건너뛴다). 배치가 두 번 돌아도 손님은 한 번 받는다.

**매시 틱은 배치 통합 설계의 ① 단계다** (`README.md` "운영: 마이그레이션과 배치"). 한 작업이 실패해도
다음은 돌리되 **응답은 500** — Scheduler 재시도와 알림이 거기 걸려 있어 200 으로 삼키면 며칠씩 조용히 안 돈다.
