# 예약 위젯 (에픽 #11) — 설계 기록

정본은 `majubom-docs/02_기능명세서.md` FR-SITE-020. 명세가 정하지 않은 것을 여기서 어떻게 정했는지만 적는다.
지금 있는 것은 **[1] 상품·이용시간·인원(#79) · [2] 날짜 · [3] 시간(#80) · [4] 담당자(#81)** 다.

```
widget/data.ts          공개 읽기 — 상품·자원·정책. 게이트는 새로 만들지 않는다
widget/state.ts         단계 판정 · 주소 ↔ 선택. 순수
widget/format.ts        날짜·시각 문구. 순수. 시각은 언제나 **가게 시계**
widget/slots-client.ts  슬롯 API 호출 규칙 (조회 구간 · 자원 파라미터)
widget/BookingWidget.tsx 셸 — 주소를 읽고, 달 단위로 슬롯을 한 번 읽는다
widget/steps.tsx        단계별 화면
app/site/[slug]/book    내부 경로. 손님이 보는 주소는 /@{slug}/book
```

## 결정한 것

**게이트를 두 번 만들지 않는다.** 위젯은 `loadPublicHome` 이 `null` 이 아닐 때만 열린다 — 승인·정지·차단·
내려둔 홈·정보 미완성 판정이 전부 거기 한 곳에 있고 `react.cache()` 로 감싸져 있어 같은 요청에서 두 번 돌지 않는다.
두 번째 판정을 두면 언젠가 둘이 어긋나고, 어긋나는 쪽이 "홈은 404 인데 예약은 받는다" 이면 최악이다.

**선택은 전부 주소에 있고, 단계는 저장하지 않는다.** 컴포넌트 상태로 들면 뒤로가기가 위젯을 통째로 닫고(#85),
카카오 로그인처럼 앱을 다녀오면 사라진다(#83 이 서버 토큰을 쓰는 이유와 같은 사정). 단계는 선택에서 **유도한다**
(`stepOf`) — 저장하면 "3단계인데 날짜가 없다" 같은 상태가 만들어진다.
**방문 기록은 단계가 바뀔 때만 남긴다.** 칩 하나 누를 때마다 쌓으면 뒤로가기 다섯 번이 1단계 안에서만 오간다.

**앞 단계를 바꾸면 뒤 단계는 버린다**(`change`). 인원이나 이용 시간이 바뀌면 그 시각이 아직 가능한지 알 수 없다.
남겨 두면 손님은 고른 적 없는 시각으로 확인 화면에 도착한다. 주소를 손으로 고쳐 온 경우도 같은 규칙을 탄다
(`readSelection` 은 모르는 값을 400 대신 **조용히 버리고**, 뒤따르는 선택도 같이 버린다).

**유형 3변형은 저장된 값이 아니라 세 스위치에서 나온다** — `guessPreset` 하나를 콘솔과 같이 쓴다.
담당자를 어디서 고르는지도 `resourceSelectMode` 가 정한다:

| 모드 | 어디서 | 왜 |
|---|---|---|
| `REQUIRED`(공간형) | **[1]** | 슬롯 조회의 **입력**이다. 시간 뒤로 미루면 API 가 `RESOURCE_REQUIRED` 로 400 이다 |
| `OPTIONAL`(담당자형) | [4] | "이 시각 가능한 분" 만 보여 주므로 되돌아갈 일이 없다 (명세 단계 순서의 근거) |
| `AUTO` · `NONE` | 없음 | `AUTO` 는 자원 목록 자체를 안 내려보낸다 (FR-PRD-010, 슬롯 API 와 같은 규칙) |

**슬롯은 달 단위로 한 번 읽는다.** 날짜 칸마다 물으면 한 달에 서른 번이고, 시간 격자는 이미 읽은 그 달에서
꺼내 쓰므로 **3단계에는 요청이 없다**. 조회 구간은 `[max(그달 1일, 오늘), min(그달 말일, 오늘+maxAdvanceDays)]` —
정책 밖은 애초에 묻지 않는다. 응답에는 **어떤 요청의 것인지**를 같이 담는다(`got.key`). 안 그러면 달을 넘긴 직후
옛 달의 슬롯이 새 달 격자에 잠깐 칠해진다. 로딩도 "아직 이 키의 응답이 아니다" 로 유도한다 — effect 안에서
setState 를 하지 않으니 계단식 렌더가 없다.

**"아직 못 읽었다" 와 "마감" 은 다른 상태다.** 달력은 응답이 오기 전에는 칸을 비활성으로 두되 회색 "휴무" 로
칠하지 않는다. 4단계도 마찬가지로 로딩 중에는 "가능한 담당자가 없다" 고 말하지 않는다.

**회차는 시각 하나에 카드 하나다.** FIXED 상품의 `excluded` 는 자원마다 한 줄이라 그대로 그리면 "20:00 만석" 이
세 줄로 뜬다. 열린 자리가 있으면 닫힌 쪽은 감추고, 전부 닫혔으면 가장 덜 나쁜 사유 하나만 남긴다.

**화면의 시각은 손님 기기가 아니라 가게 시계다.** 해외에서 열어도 "10:00" 은 가게의 10시다 — 조용히 어긋나면
손님이 한 시간 늦게 온다. 그래서 날짜 화면에 타임존을 한 줄 적어 둔다.

**받을 사람이 없는 상품에는 링크를 걸지 않는다.** 공개 홈의 `bookable`(활성 자원 연결 여부)과 위젯의 상품 목록은
같은 조건이어야 한다 — 어긋나면 손님이 멀쩡해 보이는 카드를 눌러 404 에 도착한다. `tests/db/booking-widget.test.ts`
가 둘이 같은지 본다.

**달력에 `role="grid"` 를 쓰지 않는다.** 제대로 된 grid 는 row 래핑과 방향키 이동까지 갖춰야 하는데,
반쪽짜리 롤은 스크린리더에 "표인데 행이 없다" 로 읽혀 안 붙인 것만 못하다. 버튼마다 날짜와 상태를
`aria-label` 로 읽어 주는 편이 정직하다. 방향키 이동은 #85 에서 제대로 붙인다.

**위젯은 색인하지 않고 공유 캐시에도 올리지 않는다.** 손님이 검색으로 도착할 자리는 가게 홈이고 여기는 그 홈에서
들어오는 화면이다. 프록시도 `/@{slug}` 한 장만 `public, s-maxage=60` 을 싣는다(`isPublicHome`) — 위젯은 선택 상태와
(곧) 로그인 여부에 따라 달라져 CDN 에 올리면 남의 화면이 배달된다.
